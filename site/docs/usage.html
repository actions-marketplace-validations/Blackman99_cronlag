Usage

Report

cronlag                                   # repo from the git remote of the current directory
cronlag owner/repo --days 14
cronlag owner/repo -w nightly.yml -f markdown   # paste into an issue

One block per scheduled workflow: the cron line(s), a strip with one glyph per slot (bar height = lag, ✕ = no run, ? = no run yet), lag min/median/p90/max, on-time and within-1-hour counts, a verdict, and the cause checks with the fix to apply.

Longer windows: --since and the run cache

cronlag owner/repo --since 2026-08-15          # since a UTC date: before vs. during the incident
cronlag owner/repo --since 2026-08-15T06:00Z   # or a date-time (no zone = UTC)
cronlag owner/repo --since 90d                 # relative: 36h, 30d, 6w
cronlag org my-org --since 30d -f markdown

--since replaces --days (giving both is an error); either one goes up to 400 days. Every run in the window is read: the window is split into UTC days and fetched as a few created= range queries, halved automatically wherever one would pass the API's 1000-result cap, so an every-5-minutes schedule over a year is complete too. Past about 3 lines the slot strip folds several consecutive slots into one mark, and the line under it says how many: ✕ when none of them ran, a small x when some ran and some didn't (a schedule GitHub is thinning out), otherwise the bar of the worst lag.

Run cache. A workflow run's creation time never changes, so a UTC day that ended more than 6 hours ago and whose runs have all completed is final. cronlag keeps such days on disk, one small JSON file per repo + workflow + event + day, and the next report only asks the API for today, the last day or two and any day that still had a queued or running run. The second --since 90d on the same repo costs about as much as a 2-day report.

--no-cache (or CRONLAG_NO_CACHE=1) skips reading and writing it. Deleting the directory is always safe. It holds run ids, numbers, URLs, status and timestamps (no tokens, no logs), in files only your user can read. catchup and guard never use the cache: they decide what to dispatch or skip from the API's answer right now. The GitHub Action doesn't cache either (each job starts on a fresh runner). A run that is re-run later keeps its first attempt in the cache.

Org-wide scan

cronlag org my-org
cronlag --org my-org --days 14 --fail-on late
cronlag org my-org --since 2026-09-01 -f markdown

Lists every non-archived repo in the org, finds those with on: schedule workflows, runs the same report pipeline on each (in --lite mode for fewer API calls), and prints a compact summary sorted worst first. Text, JSON and Markdown are supported; --fail-on exits 1 if any scanned repo hits the threshold. Progress goes to stderr when the terminal is a TTY. Archived repos are skipped; non-archived forks are still scanned (the fork cause check explains why schedules never fire).

Catch-up

cronlag catchup owner/repo              # dry run: what would be dispatched
cronlag catchup owner/repo --dispatch   # do it

For each scheduled workflow, cronlag takes the latest slot older than the grace period (--grace, default 15m) and younger than 24h. If neither a scheduled run nor a workflow_dispatch run was created after it, --dispatch starts the workflow on the default branch. Running it again does nothing until the next slot is due, so call it every 10–15 minutes from a scheduler that isn't GitHub's: cronlag worker prints one ready to install. If one dispatch fails (say, a token without Actions: write), the others still go out and the command exits 3.

The workflow must have a workflow_dispatch: trigger.

cronlag worker: a scheduler that isn't GitHub's

cronlag worker owner/repo -o cronlag-cf                  # Cloudflare Worker: worker.js + wrangler.toml
cronlag worker owner/repo -t systemd -o units            # systemd .service + .timer
cronlag worker owner/repo -t crontab                     # one crontab line
cronlag worker owner/repo -w nightly.yml --every 15m --grace 20m

It reads the repo's workflows once, keeps the scheduled ones that have workflow_dispatch (or the ones you name with -w), and prints a scheduler that runs exactly one cronlag catchup --dispatch pass every --every (default 10m, at minute 4 and every 10 after, off GitHub's busy :00). Same rules as above: only the latest slot past --grace, once, never inside the grace period. Without -o the file goes to stdout and a summary to stderr; -o <dir> writes the files. The token never goes into the output: it comes from a Worker secret, a root-only EnvironmentFile, or a chmod 600 env file. Use a fine-grained token for that one repo with Actions: read and write.

Guard: no double runs

When GitHub's late scheduled run finally arrives after catch-up already ran that slot, the guard tells it to skip:

jobs:
  guard:
    runs-on: ubuntu-latest
    permissions: { actions: read, contents: read }
    outputs: { skip: ${{ steps.g.outputs.skip }} }
    steps:
      - id: g
        uses: Blackman99/cronlag@v0
        with: { mode: guard }
  work:
    needs: guard
    if: needs.guard.outputs.skip != 'true'
    runs-on: ubuntu-latest
    steps:
      - run: echo "the real job"

On non-schedule events the guard always says skip=false. It also outputs slot and lag-minutes for this run.

Explain a cron line

cronlag explain "0 */6 * * *"
cronlag explain "30 5 * * 1-5" --tz America/New_York -n 10

GitHub Action (report)

on:
  schedule: [{ cron: "41 7 * * 1" }]   # weekly; yes, a schedule — it reports on all the others
  workflow_dispatch:
permissions: { actions: read, contents: read }
jobs:
  lag:
    runs-on: ubuntu-latest
    steps:
      - uses: Blackman99/cronlag@v0
        with:
          days: 7            # or since: 2026-09-01 / since: 30d
          fail-on: dropped

Writes the Markdown report to the job summary and sets outputs verdict, missed, median-lag-minutes, json.
